# NARU 新規記事：ユーザー操作2回の運用契約

この文書は、既存の Article Factory が作る記事PRの**後段**も含めた運用手順です。
記事38（PR #18）の運用で確認した手順を一般化します。記事38のSHA・タイトル・日付を次の記事に流用しません。

## ユーザーが行うこと

1. 朝の候補から記事を1件選ぶ（新規記事タブの「この記事を作る」、またはこの会話で候補IDを指定）。
2. 記事固有のプロンプトを使って、アイキャッチ1枚＋本文図解3枚を生成し、4枚をこの会話に添付する。

公開時刻を指定したいときは候補選択時または画像提出時に併記できます。指定がなければ、全ゲート通過後に公開します。候補再生成、画像の変換・命名・GitHub/Driveへの保存、PR編集、チェック確認、マージ、表示確認をユーザーに依頼しません。

**現行実装の境界:** 候補生成→記事PR/CIまでがVercel Workflow。画像添付は会話側に届き、VercelのWorkflowへ自動転送されません。以下の「画像受領以降」は担当エージェントがこの手順を実行する必要があり、現時点で無人のサーバー側連結を実装済みと称してはなりません。

## 実行状態とゲート

| 状態 | 自動側がすること | 次へ進む条件 |
|---|---|---|
| 候補提示 | 毎朝の保存済み候補を提示。blocked候補は選択不可 | ユーザーの候補選択 |
| 記事生成 | 既存Workflowで調査・出典・執筆・QA・記事PR・CI。再実行によるAPI浪費を避ける | QA FAILなし、記事PRがOpen、検証成功 |
| 画像待ち | PRのimage-planと実際の本文に基づき、4枚分の個別プロンプトを提示 | ユーザーが4枚を添付 |
| 画像準備 | 4枚の役割を確認し `npm run image:prepare:all -- <slug> <card> <01> <02> <03>`。既存画像は上書きしない | WebP 1200×630 1枚・1200×675 3枚、EXIF/XMP/IPTC/ICC/commentsなし |
| 画像監査 | 人間が見える画像内のAIロゴ・透かし、誤字、判読不能文字、実在ロゴ、見切れ、本文との不一致を個別に確認 | 4枚とも合格。メタデータ除去だけで見えるロゴは消えない |
| 保存・PR反映 | 記事単位のGoogle DriveフォルダにMarkdown＋4枚を保存。画像と本文のalt・配置を記事PRに反映 | Drive内の実ファイルとPRの画像パスを照合 |
| プレビュー監査 | 新head SHAのCIとVercel Previewを待ち、記事H1/H2/本文/出典/リンク/4画像/OG/モバイル表示を実ブラウザで点検 | FAIL 0、見出し記号の露出なし、4画像のnaturalWidth > 0 |
| 公開待ち | 指定時刻があればその時点で**再取得**してゲート再評価 | PR Open・非Draft・未マージ・mergeable、head SHA不変、最新validationとVercel statusがsuccess |
| 公開確認 | 指定PRだけsquash merge。merge SHAのProduction成功と公開URLのH1・4画像表示を確認 | 成功後にだけ「公開完了」と報告 |

### 例外は安全停止

- `ARTICLE_FACTORY_AUTO_PUBLISH` はOFFのまま。画像のない初期PRを既存Workflowが自動マージしないことが前提。
- PRのheadが画像監査時点から変わったら、古いチェック結果・古いプレビューでマージしない。新headで全検証をやり直す。
- QA FAIL、出典不足、未検証の体験談、CI/Vercelの欠落・失敗、画像不足、Drive保存失敗、プレビュー差異があれば公開しない。
- 公開予約は事前のチェック成功だけを信用しない。実行時にPRとhead SHAと最新チェックを取り直す。予定時刻に条件未達なら勝手に延期・別PRへ切り替えない。
- GitHubでマージされたが本番デプロイに失敗した場合は「マージ済み／公開未確認」と報告し、二重マージや別のデプロイを自動実行しない。
- 画像生成はユーザー側のみ。画像が欠けている場合、代わりの生成や素材変更はしない。
- LLMのquota枯渇は恒久エラーとして止める。候補・記事の無断再生成はしない。

## 記事ごとの永続記録

記録には少なくとも `batchId`、`candidateId`、`runId`、記事slug、PR番号・現在head SHA、DriveフォルダURL、画像4枚のファイル名とSHA-256、画像監査結果、PRチェック結果、希望公開時刻とタイムゾーン、merge SHA、Production結果、公開URLを残します。secret、元画像のEXIF、OpenAI応答全文は保存しません。

同じ記事・同じ画像を再受領した場合は既存の成果物を再利用します。別の画像に差し替える場合はPR headが変わるので、プレビュー監査と公開ゲートを初めからやり直します。

## 実装の残作業（無人化する場合）

会話の画像添付をVercelに転送する認証済みの入力経路、Driveの書き込み資格情報、記事単位の永続状態と画像待ちhook、PR更新後の検証・指定時刻の耐久待機が必要です。これらが揃うまで「候補を選んだだけで、会話に画像を添付してもサーバーが自動的に公開する」とは表示しません。現行の会話エージェントによる運用では、ユーザーの追加手作業なしに後段を代行します。
