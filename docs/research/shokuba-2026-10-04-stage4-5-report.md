ただし下記3.5の精度上の留保がある。

### 3.5 「1求人=1レコード」の達成度（精度検証の本題）

| 指標 | 値 |
| --- | --- |
| 職種名を含むタイトルのレコード | **133 / 248（53.6%）** |
| 「新卒採用」「中途採用」など募集区分名のレコード | 残り46.4%の多く |
| 同一企業内でタイトルが重複 | 19件 |
| jobTitleの出所: h1/h2 / アンカー / ページtitle / JSON-LD | 152 / 67 / 11 / 18 |

タイトル上位は「新卒採用」12・「中途採用」10・「採用情報」8 など、
**職種ではなく募集区分やページ名が残っている**。
取得率100%のjobTitleのうち、職種名として使えるのは約半分。

原因は構造的なもので、日本の中小IT企業の採用ページは

- 職種ごとの詳細ページを持たず、1ページに全職種を並べる
- 「新卒採用」「中途採用」の2ページしか無い
- h1がサイト全体の見出し（「Recruit 採用情報」）のまま

というパターンが多い。JobPosting JSON-LDが0.5%しかないのも同じ理由である。

本パイロットでは「社員インタビュー」「エントリーフォーム」「福利厚生」などを
221件除外して精度を上げたが、**これ以上はHTML解析の一般ルールでは伸びない。**

## 4. 3,419社への拡大判断

### 4.1 コスト見積（パイロット実測の線形外挿）

| 工程 | 実測 | 3,419社への外挿 |
| --- | --- | --- |
| Stage 4 | 300社 / 259.3秒 / 0.86秒per社 | **約49分 / 約7,000リクエスト** |
| Stage 5 | 202社 / 182.0秒 / 0.90秒per社 | **約37分 / 対象約2,439社 / 求人約3,000件** |
| 合計 | — | **約1.5時間** |

同時実行数8・同一ホスト1.5秒間隔・1ホスト同時1リクエストを変えない前提。
有料APIもクラウドも不要で、このマシンのネットワークだけで完了する規模。

### 4.2 判断

**Stage 4は拡大する。** 理由:

1. 母数が196社→約2,400社（12倍以上）。これが最大の価値
2. 発見率71%は地域に依存せず、規模別の差も説明可能
3. 1.5時間で1スナップショットが取れるので四半期ごとの定点観測が現実的
4. 403が5件・429が0件・robots blockが1件で、サイト側に迷惑をかけていない

**Stage 5は拡大前に改良する。** 理由:

1. 求人レコードの53.6%しか職種名を持たず、「1求人=1レコード」が半分しか成立していない
2. 1社あたり中央値1件では、職種×第二新卒×年収のクロス集計に耐えない
3. salaryMin 22.6%・experienceYearsMin 16.1%という取得率では、年収や必要経験の分布を記事に出せない
4. 今拡大すると「約3,000件の半分が募集区分名のレコード」になり、後から作り直すことになる

### 4.3 Stage 5の改良案（拡大前にやること）

1. **`isJobLevelRecord` の判定順を直す。** 現在は職種トークンを先に見るため、
   「社員インタビュー｜エンジニア」型の見出しが通過する。NOT_A_JOB_TITLEを先に判定する
2. **1ページ内の複数求人を分解する。** 「1ページに全職種」型が多数派なので、
   `<table>`/`<dl>`/見出し単位で募集職種ブロックを切り出し、ブロック単位でレコード化する。
   これが最も効果が大きい
3. **募集区分レコードと職種レコードを型として分ける。** `recordLevel: 'job' | 'hiringTrack' | 'page'`
   を持たせ、集計時に混ぜない
4. **公式ATSを優先経路にする。** 件数は3社と少ないが、ATS上のページは職種単位で構造が安定している
5. **1社あたり上限8件を規模別に調整する。** 100-299人帯は到達率71.1%と最も高く、上限に当たっている社がある

### 4.4 拡大時の運用条件（変えない）

- 同時実行数8 / 同一ホスト1.5秒間隔 / 1ホスト同時1リクエスト / タイムアウト20秒 / リトライ1回
- robots.txtをリダイレクト各ホップで再評価、明示的Disallowは取得しない
- 403/429/404は記録のみ。突破しない
- URL総当たり、検索エンジンのスクレイピング、CAPTCHA/bot対策回避はしない
- 第三者求人媒体（Indeed・求人ボックス・OpenWork・転職会議・マイナビ・リクナビ等）は
  URLと事実のみ記録し、横断クロールしない
- HTML全文・求人本文は保存しない
- 未取得値はnull。0やfalseにしない

## 5. 副産物として得られた記事ネタ

Stage 1〜3のレポート（`shokuba-2026-10-04-report.md`）の候補に加えて、Stage 4/5から新たに出たもの。

1. **「国のデータベースに載っている大手IT企業のHPを開いたら、404と下層ページだらけだった」**
   1,000人以上38社のうち11社で企業HPが取得できず、内訳は404・DNS解決不可・下層ページ登録。
   母数を明示すれば面白く、企業研究の実務的な注意喚起になる（母数38社と小さいので断定しない）
2. **「IT企業の求人票で『第二新卒』と書いてあるのは27件に1件」**
   求人レコード248件中9件（3.6%）。企業単位の11.0%との差が論点。
   ※Stage 5の精度留保（53.6%）を明記した上でなら使える
3. **「採用ページはあるのに、求人票にたどり着けない会社が半分」**
   採用ページを発見できた202社のうち、求人詳細に到達できたのは106社（52.5%）。
   求職者が「何に応募できるのか分からない」状態の定量化
4. **「地方のIT企業も採用情報は出している」**
   発見率は東京67.6%・主要都市圏63.7%・その他71.9%でほぼ差がない。
   「地方は情報が少ない」という通説の反証
5. **「IT求人の約半分は給与が書かれていない」**
   求人レコード248件中、給与・年収・月給への言及は137件（55.2%）。
   金額が構造化値として取れたのは56件（22.6%）のみ

いずれも**記事化はこのレポートの範囲外**。執筆は行っていない。

### ユニットテストで実際に見つけた不具合

テストは形式だけでなく、実データに影響する2件のバグを捕まえた。

1. **`extractLocation("勤務地：東京都渋谷区")` が「東京都 | 京都」を返していた。**

   汎用的な採用ページ見出しを0点、職種名を2点、募集区分名を1点でスコアリングし、

## 8. 既知の問題 / 判断が必要な項目

1. **Stage 5の求人単位化が53.6%止まり。** 4.3の改良（特に1ページ内複数求人の分解）が前提。
   このまま3,419社へ拡大すると作り直しになる
2. **`isJobLevelRecord` の判定順。** 職種トークンを先に見るため「社員インタビュー｜エンジニア」型が通過する。
   本パイロットのデータはこの順序で生成されているため、**コードを先に直すと
   コミット済みデータと再現しなくなる**。拡大ランと同時に直すのが安全
3. **JobPosting JSON-LDが0.5%。** 構造化データ経由の正確な求人取得は中小IT企業では当てにできない
4. **年収・必要経験年数の母数が小さい**（33件・40件）。記事で分布や平均を出せない
5. **ルートフォールバックを主集計に合算していない。** 拡大ランでは有効のまま実行される（+3.3pt見込み）
6. **しょくばらぼの企業HP欄が大企業で劣化している。** 拡大時は404・下層ページの扱いを
   あらかじめ決めておく必要がある
7. **`requiredSkills` / `preferredSkills` の抜粋が次セクションに流れ込む例が残る。**
   打ち切り語に「勤務先」が入っておらず、勤務地情報まで含んだレコードがある。
   フィールド長は160字で上限がかかっているため求人本文の保存には至っていない。
   2と同じ理由で、拡大ランと同時に打ち切り語を追加する
7. 記事化・公開・masterへのmergeは行っていない
